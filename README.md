# 결계 (GYEOLGYE / WARD)

판정(Assessment)과 검증(Runtime Detection)을 잇는 도구. 금융회사가 내부업무망에 SaaS를 도입할 때 필요한 "이용자의 고유식별정보 또는 개인신용정보를 처리하지 않을 것" 요건(전자금융감독규정 시행세칙 제2조의3 제1항 제3호, 2026.4.20 신설)의 검토를 구조화한다. 데모 단계.

## 배경

2026년 4월 20일 시행세칙 개정으로 금융회사는 혁신금융서비스 지정 없이 내부업무망에서 SaaS를 쓸 수 있게 됐다. 진입 관문인 위 요건에서 '처리'의 정의는 감독규정과 시행세칙 어디에도 없고, 금융보안원 CSP 안전성 평가는 처리 관련 항목을 평가범위에서 제외하며(FAQ 첨부2), 판정 기준 수립은 각 금융회사에 위임되어 있다(해설서 6장). 이 도구는 그 판정을 답할 수 있는 질문들로 분해하고, 판정이 남긴 빈틈을 운영 중 탐지로 메운다.

## 구성

```
index.html    판정 워크벤치(W) + 운영 중 검증 데모. 서버 없이 열린다
engine.js     결합 탐지 엔진(D). 브라우저와 Node 양쪽에서 동작
extension/    크롬 확장 — 실시간 입력 감시 (해설서 "입력 시 사전 필터"의 보완통제)
scan.js       배치 스캐너 — 저장 문서 주기 점검 + 반기 증적 리포트 생성
eval/         측정 하네스(L). 합성 문서 생성 + 정밀도·재현율 채점
SPEC.md       명세: 네 요소(W/D/E/L), 파이프라인, 불변 원칙
```

해설서가 요구하는 통제의 전체 주기가 코드로 구현되어 있다: 도입 전 판정(index.html) →
입력 시점 경고(extension) → 저장분 주기 점검(scan.js) → 반기 자체평가 증적(리포트).

데모와 측정 하네스가 **같은 엔진**을 쓴다. 시연한 것과 측정한 것이 갈라지지 않게 하기 위해서다.

## 실행

판정 워크벤치는 `index.html`을 브라우저에서 열면 된다. 빌드도 서버도 필요 없다.

측정은 Node로 돌린다.

```bash
node eval/run.js --docs 30
```

### 실시간 감시 (크롬 확장)

`chrome://extensions` → 개발자 모드 켜기 → "압축해제된 확장 프로그램을 로드" → `extension/` 폴더 선택.
Notion·Slack·Teams·Zoom·두레이 웹에서 입력창에 고객 정보와 신용정보가 결합된 문장을 치면
입력창이 붉게 표시되고 경고 배너가 뜬다. 판단은 전부 브라우저 안에서 끝나며 네트워크 전송이 없다.
탐지 기록은 마스킹되어 저장되고, 확장 아이콘 → "기록 내보내기"로 증적 CSV를 뽑는다.
`extension/engine.js`는 루트 `engine.js`의 복사본이다. 엔진을 고치면 복사해서 동기화한다.

### 주기 점검 (배치 스캔)

```bash
node scan.js <문서폴더>            # 규칙+휴리스틱
node scan.js <문서폴더> --llm      # 로컬 LLM 결합 판단 포함
```

`ward-report/`에 점검 리포트(md·json)가 생성된다. 발견 내역은 마스킹되고(긴 숫자열은 끝 4자리,
이름은 가운데 글자) 원문 위치는 파일·줄 번호·해시로 특정된다. 리포트에는 근거 조문, 조치 지침,
서명란이 포함되어 반기 자체평가에 그대로 첨부할 수 있다. 위반 발견 시 종료코드 2를 반환하므로
크론·CI에 걸어 주기 점검을 자동화할 수 있다.

## 탐지 엔진의 3층

| 층 | 대상 | 방법 | 성격 |
|---|---|---|---|
| 규칙 | 주민번호, 카드번호, 연락처 | 정규식 + 체크섬·Luhn 검증 | 결정적. 브라우저에서도 동작 |
| 식별정보 | 이름 등 | 호칭 패턴 + 지시어 제외 | "해당 고객" 같은 지시어를 이름으로 잡지 않는다 |
| 결합 | 식별정보 × 신용정보 문맥 | 로컬 소형 LLM (없으면 규칙 근사) | 문맥 이해가 필요한 지점 |

위반 확정은 LLM이 아니라 코드가 한다. LLM 출력은 근거 스팬이 원문에 실제로 존재하는지 검증한 뒤에만 후보로 채택된다(환각 차단). 감사 증적은 같은 입력에 같은 결과가 나와야 하기 때문이다.

## 측정 결과 (합성 문서 30건, 위반 정답 84건, seed=20260810)

Kanana-2-3B, Apple M4 Pro CPU 추론 기준. 방법별 소요는 LLM 포함 시 30문서에 약 90초.

| 방법 | 정밀도 | 재현율 | F1 | TP | FP | FN |
|---|---|---|---|---|---|---|
| 규칙층만 | 100.0% | 42.9% | 60.0% | 36 | 0 | 48 |
| 규칙 + 휴리스틱 | 100.0% | 59.5% | 74.6% | 50 | 0 | 34 |
| 규칙 + LLM | 86.8% | 78.6% | 82.5% | 66 | 10 | 18 |
| **합집합 (실서비스 구성)** | **87.5%** | **83.3%** | **85.4%** | 70 | 10 | 14 |

케이스 유형별 재현율에서 이 프로젝트의 핵심 근거가 나온다.

| 유형 | 규칙층만 | 규칙+휴리스틱 | 합집합 |
|---|---|---|---|
| 주민번호 | 100% | 100% | 100% |
| 카드번호 | 100% | 100% | 100% |
| 결합 (같은 줄) | 0% | 92.9% | 92.9% |
| 결합 (줄 넘김) | 0% | 0% | **57.1%** |
| 결합 (지시어 연결) | 0% | 5.0% | **65.0%** |

읽는 법은 이렇다.

주민번호와 카드번호는 규칙층이 100% 잡는다. 형식이 정해져 있고 체크섬으로 검증되기 때문에 LLM이 필요 없다. 반대로 같은 줄 안의 결합은 휴리스틱이 92.9%로 충분하다. 이름과 신용 어휘가 한 줄에 있으면 근접만 봐도 되기 때문이다.

문제는 나머지 둘이다. 줄을 넘어가는 결합("정해나 고객 재방문" + 다음 줄 "해당 고객은 연체 이력")과 지시어로 이어지는 결합은 규칙으로 각각 0%, 5%다. 근접이나 패턴으로는 지시관계를 풀 수 없기 때문이고, 이건 규칙을 더 정교하게 만들어서 해결되는 종류가 아니다. 이 두 유형이 전체 위반의 40%를 차지한다. LLM을 넣으면 57.1%와 65.0%가 된다.

즉 이 프로젝트가 LLM을 쓰는 이유는 "AI를 쓰면 좋아서"가 아니라, 규칙이 구조적으로 도달할 수 없는 영역이 위반의 40%이기 때문이다. 그리고 그 영역이 정확히 신용정보법 제2조의 결합 요건이 만들어낸 영역이다.

정밀도가 100%에서 87.5%로 내려가는 것은 감수한 교환이다. 미탐은 곧 규제 위반이고 오탐은 담당자가 한 번 더 확인하면 되는 비용이다. 다만 경고 피로를 막기 위해 오탐률은 계속 측정한다.

### 검증층이 걸러낸 것

| 사유 | 건수 | 뜻 |
|---|---|---|
| combined_missing_parts | 25 | 결합이라 라벨링했으나 누구의 무슨 정보인지 못 채움 |
| identifier_not_in_span | 3 | 근거 스팬 밖의 이름을 끌어다 붙임 |
| span_not_in_source | 3 | 원문에 없는 근거를 지어냄 |

폐기 31건은 손실이 아니라 검증층의 작동 지표다. 실제로 폐기된 것들은 "5월 여신협의회 회의록"(문서 제목), "카드 재발급 요청 접수"(사람 없는 줄)처럼 결합으로 볼 수 없는 것들이었다.

### 시도했다가 되돌린 것

빈 필드를 코드가 스팬·창에서 뽑아 채우는 보정을 넣어봤으나 측정 결과 악화되어 제거했다. 보정 7건이 전부 오탐이었고 재현율은 그대로, 정밀도만 86.4%에서 79.5%로 떨어졌다. 모델이 사람 없는 줄을 결합으로 라벨링할 때 보정이 무관한 옆줄 이름을 끌어와 붙인 탓이다. 대신 검증을 조여서(지목한 이름이 근거 스팬 안에 있어야 인정) 정밀도를 86.4%에서 87.5%로 올렸다.

### 남은 미탐 14건

같은 줄 1건, 줄 넘김 6건, 지시어 연결 7건. 이 유형들이 다음 세대 합성 문서의 집중 생성 목표가 된다.

## 로컬 LLM 연결

```bash
brew install ollama
OLLAMA_ORIGINS="*" ollama serve          # 브라우저 데모에서 호출하려면 origin 허용 필요
ollama pull hf.co/mradermacher/kanana-2-3b-instruct-GGUF:Q4_K_M
ollama pull hf.co/mykor/Midm-2.0-Base-Instruct-gguf:Q4_K_M   # 대조군
```

모델이 뜬 상태에서 `index.html`을 새로고침하면 검증 데모에 LLM 모드가 열린다. 측정은 이렇게 돌린다.

```bash
node eval/run.js --llm --docs 30
```

기본 모델은 카카오의 **Kanana-2-3B** (2026.07)다. 국내 공개 모델 중 가장 최신이고 Q4 기준 2.2GB로 가볍다. 강점이 한국어(HAE-RAE, KMMLU)와 코딩, 약점이 수학이라 이 과제와 방향이 맞는다. 우리가 쓰는 능력은 한국어 문맥 이해와 스키마 준수·문자열 정확 복사이고 수학은 쓰지 않는다. 크기가 작아 금융사 단말 배포 시나리오로 그대로 이어진다는 것도 이점이다.

대조군은 KT의 **Mi:dm 2.0 Base (11.5B, MIT)**다. Ko-IFEval 82로 지시 준수 근거가 있고 Q4 7GB다. 3B가 결합 판단에서 무너지면 이쪽으로 올린다.

| 모델 | 크기 | 라이선스 | 공개 | 비고 |
|---|---|---|---|---|
| Kanana-2-3B (카카오) | 3B / 2.2GB | Kanana Open | 2026.07 | 기본값. 자기 서비스 운영 자유, 제3자 재판매만 별도 계약 |
| Mi:dm 2.0 Base (KT) | 11.5B / 7GB | MIT | 2025.07 | 대조군. 제약 없음 |
| Tri-21B-Think (트릴리온랩스) | 21B / 12.6GB | Apache 2.0 | 2026.02 | 예산 내 최대. 사고형이라 JSON 후처리 필요 |
| EXAONE 4.x (LG) | 32B+ | NC | | 상업 이용 금지, 크기도 초과 |

두 모델을 한 번에 비교하려면:

```bash
node eval/run.js --llm --models hf.co/mradermacher/kanana-2-3b-instruct-GGUF:Q4_K_M,hf.co/mykor/Midm-2.0-Base-Instruct-gguf:Q4_K_M --docs 30
```

## 측정 방법: 생성이 곧 라벨

실제 금융 문서는 그 자체가 개인신용정보라 측정에 쓸 수 없다. 대신 위반을 직접 심어 문서를 만든다. 무엇을 어디에 심었는지 알기 때문에 정답지가 라벨링 비용 없이 생긴다. 놓친 유형은 다음 세대 생성 목표로 되먹여 어려운 케이스를 증식시킨다.

같은 seed면 같은 데이터가 나온다. 실험 재현을 위해서다.

## 고지

본 도구는 법적 판단을 대행하지 않는다. 판단에 필요한 근거와 구조를 제공할 뿐이며, 최종 판단과 책임은 검토자와 소속 기관에 있다. SaaS별 근거 데이터는 2026년 8월 각 벤더 공개 관리자 문서 조사 기준이며 요금제와 기능은 변경될 수 있다.
